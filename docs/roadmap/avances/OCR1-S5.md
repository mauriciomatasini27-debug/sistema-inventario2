OCR1-S5 parcial: la ingesta vive una sola vez en `src/lib/ocr-ingesta.ts` (`ingerirOcr` + `respuestaIngesta`) y `POST /api/ocr/jobs` quedó como cáscara con el mismo contrato HTTP; decisión: el webhook reconoce `image`/`document` de la Cloud API (`normalizarAdjuntoEntrada`, media id + mime_type), valida el mime (415 + texto corto si no es comprobante, sin job) y descarga el media con las credenciales del número central (`descargar_media`, dos saltos: metadata y binario), entregando los bytes como `ImagenOcr` al motor OCR (el body del motor ya no lleva referencia, solo bytes en base64 + mime); el job, el borrador y el evento conservan `wa-media:<id>` como referencia de auditoría, y si la descarga falla el bot responde un mensaje de reintento sin crear job; llama la ingesta con Idempotency-Key = wamid, `origen: "wa"`, `bytes_ref: "wa-media:<id>"` y `es_comprobante: true`, y corre todo inline en la request, sin cola; el job y el borrador quedan en el tenant del número vía `conTenant` y el mismo wamid dos veces no crea ni un segundo job ni una segunda respuesta (AT1), la oferta es un `interactive` de botones con `Confirmar` / `Editar` / `Descartar` e ids `ocr:<acción>:<borradorId>` armados por la función pura `payload_borrador_ocr` (`src/modules/whatsapp/ocr-borrador.ts`) y enviados por `enviarPayload` del transporte, y el toque de los botones no se atiende en este corte (confirmar factura es acción sensible que AU10.4 deriva a la web, y "Editar" necesita un flujo conversacional); quedan para después: el pull real de Gmail (`history.list` con OAuth de Mauri), la prueba en vivo del número central (P9-3) y el manejo del toque de botones.
