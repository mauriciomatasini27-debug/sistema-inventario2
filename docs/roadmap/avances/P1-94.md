P1-94: el admin cambia el plan de un comercio desde la ficha, y el cupo de usuarios queda atado al plan nuevo.

## Decisión
POST /api/admin/tenants/plan queda detrás de exigirAdminMutante. Pide tenant_id y un plan válido (demo, base o plus, los mismos del alta). No pide confirmo_id porque no es una acción destructiva; el motivo es optativo.
El plan se guarda en tenants (la columna ya existía; no hay migración). Si hay CONTROL_DATABASE_URL y no se puede persistir, se revierte la memoria y se responde 503.
Si el comercio tiene una suscripción de producto, se sincroniza en el acto: base y demo equivalen a básico, plus a plus. Así el resumen de plan del dueño y los cupos de features siguen el cambio. Si no hay suscripción, no se inventa una.
Bajar de plan con más usuarios que el cupo nuevo se permite: no se echa a nadie, pero las invitaciones nuevas quedan en cupo lleno. El panel avisa antes de confirmar.
El acto queda como cambio_plan con de/a (y motivo si vino).
