P10-99: guarda de revalidación antes de mutar worktrees o ramas.

## Decisión

El mismo CLI ofrece `--guarda <recibo.json>`: vuelve a leer HEAD y el estado normalizado del objetivo y decide, sin ejecutar la mutación.
El recibo cubre worktree, rama local y rama remota; el objetivo se nombra siempre en la negación con valores observados y actuales.
El estado normalizado reutiliza el parser de `status --porcelain` del módulo del informe, ordena archivos y compara también `mergeHead`.
Para ramas remotas, el estado se relee del worktree cuya rama local hace tracking de esa upstream, no de un estado vacío fijo.
Un merge cerrado por otra sesión niega el recibo viejo, aunque el HEAD coincida.
La entrada mal formada o con objetivo inexistente sale con código 2; el estado cambiado con código 1; la coincidencia con código 0 y una confirmación breve.
La guarda decide sobre el estado vivo del repo, así que no puede autorizar una operación planificada sobre valores stale.
