P10-38: `exigeReauth` tolera un atraso de hasta 60 s del reloj del servidor, para que un salto de NTP no convierta un reauth fresco en un 401 (causa del flake de auth de #448).

## Decisión
- En esta máquina el reloj del sistema retrocede ~2,7 s cada ~30 s; medido con un sampler de `Date.now()` durante 2 min: 4 saltos y `minDelta = -2743 ms`.
- `exigeReauth` calculaba `haceMin = (ahora - reauthAt) / 60000` y rechazaba `haceMin < 0`; con el salto, un `reauthAt` recién creado quedaba "en el futuro" y el POST mutante devolvía 401 `reauth_requerida`.
- El fix acepta deltas negativos de hasta `TOLERANCIA_RELOJ_MS = 60_000`; un futuro mayor sigue rechazado. La ventana de 5 min y la semántica de auth no cambian.
- Regresión: unit test en `tests/panel-admin-p36b.test.ts` y test de ruta en `tests/nivel5-admin.test.ts` que atrasa el reloj 3 s con fake timers entre la sesión y el POST (rojo contra el código anterior: 401).
- El timeout del `beforeAll` de `numeracion-ordenes-por-comercio` es el otro fix de #448 (P10-37).
